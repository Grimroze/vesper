Distributed LLM Reverse Proxy with Sliding-Window Rate Limiting, Semantic Caching & Circuit Breaker

Problem Statement & Architectural Context

Foundational

Raw large language model endpoints suffer from high latency, absence of rate limiting, and catastrophic service failure during upstream outages. Standard semantic caches fail on query negations, incorrectly returning positive responses to negated user prompts. AegisGateway solves these issues via a reverse-proxy providing sliding-window rate limiting, two-stage polarity-safe semantic caching, and automatic distributed failover.

System Architecture Blueprint

Inline Vector SVG

End-to-End Architectural Flow Sequence:

  1. 1 Client submits POST request to Gateway, RateLimiter inspects Redis ZSET via an atomic pipeline, SemanticCache encodes prompt using BGE-small and computes cosine similarity, Lexical Polarity Guard rejects negation mismatches, ModelRouter evaluates Redis circuit breaker state and calls Primary or Backup LLM, and the new response is written back to Redis with a TTL.

Step-by-Step Request Flow

7 Steps
  1. 1 The client issues an HTTP POST request to /v1/chat containing the prompt and client identifier.
  2. 2 The gateway registers the arrival timestamp and executes an atomic pipeline against a Redis Sorted Set.
  3. 3 If the user exceeds the quota within the 60-second window, the gateway raises an HTTP 429 status code.
  4. 4 Allowed requests are encoded into a 384-dimensional vector using BGE-small-en-v1.5 to scan cached Redis hashes.
  5. 5 If cosine similarity meets the 0.85 threshold and passes the lexical negation guard, cached text returns in approximately 14ms.
  6. 6 On a cache miss, the router inspects the Redis circuit breaker state to dispatch to either the primary or backup model.
  7. 7 The resulting answer is saved in Redis hashes with a 3600-second expiration, updating telemetry counters before returning.

Core Interview Questions & Answers

11 Prepared Scenarios
Q1 1. End-to-end walkthrough of one request
Question: Walk me through the lifecycle of a request entering your gateway from start to finish.
Answer: When a request hits the /v1/chat endpoint in main.py, the gateway starts a timer and extracts the client identifier. The rate limiter executes an atomic Redis pipeline to prune expired entries and count active requests in a Sorted Set. If allowed, the semantic cache encodes the query via BGE-small and performs vector dot product comparisons against Redis hashes. When a match exceeds the 0.85 threshold and passes the negation guard, the cached answer returns immediately in around 14ms. If a cache miss occurs, the circuit breaker verifies that the state is not open before dispatching the request to the primary model or cloud backup, persisting the final text in Redis.
💡 What to keep in mind
State the evaluation sequence precisely: rate limiting, then cache checking, followed by circuit evaluation, and finally cache writing. Avoid claiming vector search runs on an indexed database, as it executes via a Redis scan loop in the code.
Q2 2. Why sliding-window log vs token bucket or fixed window, and ZSET cleanup
Question: Why did you choose a Sliding Window Log using Redis ZSET over Token Bucket or Fixed Window, and how do you handle memory cleanup?
Answer: Fixed window counters suffer from boundary bursts where clients double their allowed throughput by making requests at window edges. Token buckets are lightweight but do not track individual rolling request timestamps without complex concurrency scripts. The sliding-window log in rate_limiter.py uses Redis Sorted Sets with timestamps as both score and member, allowing exact time tracking. Memory is managed in two ways: old entries are pruned on every request via ZREMRANGEBYSCORE, and an expiration key is set on the entire set via EXPIRE to remove inactive users after the window closes.
💡 What to keep in mind
The sliding-window log achieves higher accuracy at the cost of higher memory storage compared to single-counter algorithms. Emphasize that the logarithmic insertion cost remains low because the window size limits the element count.
Q3 3. Rate limiter behavior when Redis is slow or down
Question: What happens to your rate limiter if Redis experiences high latency or completely crashes?
Answer: In the current implementation, the rate limiter directly invokes Redis without a fallback exception wrapper, causing FastAPI to return an HTTP 500 error if Redis goes down. A production-grade enhancement is adopting a fail-open strategy, where network timeouts are caught, errors logged, and requests permitted through with a warning header. To handle high latency, the connection client sets a 1-second socket connection timeout to prevent incoming network connections from hanging indefinitely.
💡 What to keep in mind
Be honest about the current fail-closed behavior instead of claiming that the gateway seamlessly switches to an in-memory dictionary. Mention the trade-off between strict quota enforcement and overall gateway availability.
Q4 4. Semantic caching: Two stages and negation guard
Question: How does your two-stage caching work, and why does an embedding model fail at negation?
Answer: The first stage in semantic_cache.py encodes user queries into 384-dimensional normalized vectors using BGE-small and calculates cosine similarity using dot products. Bi-encoder models often assign low weights to stop words and negations, causing opposing queries like "how to install" and "how to not install" to score above 0.88 similarity. To fix this, stage two runs an O(1) lexical polarity guard that extracts negation tokens from both queries using set intersection. If the query polarities do not match, the gateway bypasses the cache and routes the prompt directly to the language model.
💡 What to keep in mind
Clarify that the guard handles explicit syntactic negations rather than subtle semantic sarcasm. Explain that normalizing vectors upfront reduces the cosine calculation to a simple hardware-accelerated dot product.
Q5 5. How the 2140ms to 14ms measurement was done
Question: How was the latency reduction from 2140ms to 14ms measured, and what was the baseline?
Answer: The timing was measured inside main.py across the full request lifecycle by calculating elapsed time between arrival and response transmission. The baseline was established on cold cache misses that required local Llama 3.1 inference on a standard workstation, averaging roughly 2140ms. On warm semantic hits, the gateway bypasses upstream inference entirely, completing embedding generation in about 10ms and Redis operations in 2ms, totaling roughly 14ms. The measurement reflects the entire gateway processing pipeline rather than an isolated database query.
💡 What to keep in mind
Acknowledge that the benchmark comes from internal gateway metrics rather than a large distributed load test framework. Make sure to separate model generation time from embedding latency when discussing savings.
Q6 6. Cache invalidation, TTL, and stale answers
Question: How do you handle stale cache entries and cache invalidation in your gateway?
Answer: Cache invalidation currently operates through explicit expiration timers set during write operations. In semantic_cache.py, every new Redis hash receives a 3600-second expiration via the EXPIRE command, ensuring entries automatically clear after one hour. In production environments, this can be improved by adding model version metadata to cache keys to invalidate entries when weights change. Another enhancement is domain-specific namespace purging, allowing administrators to delete relevant hash groups when underlying documentation updates.
💡 What to keep in mind
Time-to-live invalidation cannot detect real-world fact changes before expiration occurs. Highlight the tension between aggressive caching for latency reduction and fresh data requirements.
Q7 7. Circuit breaker: States, Redis sharing, and race conditions
Question: Explain your Circuit Breaker implementation in Redis. How do you manage states and concurrency?
Answer: The router in circuit_breaker.py tracks failures in Redis using atomic INCR operations on a failure key. When three consecutive failures occur, the gateway writes the circuit state key as OPEN with an expiration of 30 seconds. All gateway instances share this state, bypassing the failing primary model immediately without waiting for timeouts. After 30 seconds, the key expires automatically, resetting the state to CLOSED without requiring background coordinator threads.
💡 What to keep in mind
Note that using key expiration creates an instant jump back to CLOSED rather than a gradual half-open canary phase. Emphasize that Redis commands run single-threaded, preventing race conditions during counter increments.
Q8 8. Failover: Definition of failure and in-flight requests
Question: What constitutes a failure triggering the circuit breaker, and what happens to requests currently in-flight?
Answer: In circuit_breaker.py, the primary model call is enclosed in an exception handler that catches connection errors, socket timeouts, and HTTP status errors. When an exception occurs, the failure counter increments, and the active request falls back to the cloud model within the same execution path. The user whose request experienced the failure still receives a valid response rather than an error. Once the threshold is reached, subsequent requests skip the primary model entirely.
💡 What to keep in mind
Point out that catching broad exceptions treats client-side input errors similarly to infrastructure downtimes. Explain that the failing request is recovered using fallback execution rather than being dropped.
Q9 9. Failure modes: Redis down, both endpoints down, embedding model slow
Question: How does your system degrade under catastrophic failure modes: Redis crash, both LLMs down, or embedding model latency spikes?
Answer: If Redis crashes, the gateway fails because rate limiting and caching are inline dependencies, which can be mitigated in production using Redis clusters and fail-open handlers. If both primary and backup models fail, the fallback handler raises an error and the application returns an HTTP 500 status code. If the embedding model experiences high latency, overall processing slows down, but because the model runs locally in memory, it is protected from external network outages.
💡 What to keep in mind
Clearly distinguish between network dependencies and in-process machine learning dependencies. Discuss how graceful degradation strategies protect user experience during partial outages.
Q10 10. Scaling and trade-offs: Concurrency and Redis as shared state
Question: Why use Redis as the centralized state layer instead of in-memory dictionaries, and what are the concurrency trade-offs?
Answer: In-memory dictionaries cannot share state across multiple gateway processes running behind a load balancer, allowing users to bypass rate limits by hitting different nodes. Centralizing state in Redis ensures uniform quota enforcement, distributed circuit breaker awareness, and high cache hit ratios across horizontal replicas. The main trade-off is the introduction of a network round trip for rate and cache checks, which we minimize using pipelined execution.
💡 What to keep in mind
Focus on multi-process consistency versus single-process memory access speed. Explain that Redis pipelining groups operations into a single network packet to lower round-trip latency.
Q11 11. What I would change now
Question: Looking back at the AegisGateway codebase, what are the top architectural changes you would make today?
Answer: First, I would replace the linear scan loop in semantic_cache.py with an indexed vector engine like RediSearch or Qdrant using an HNSW index to scale beyond small datasets. Second, I would refactor synchronous route handlers and client calls in main.py to asynchronous coroutines to prevent worker threads from blocking on model inference. Third, I would implement a true half-open state with a canary probe in the circuit breaker to prevent thundering herd spikes when the primary model recovers.
💡 What to keep in mind
Proposing specific vector indexes and asynchronous programming shows senior systems awareness. Focus on performance bottlenecks that emerge at scale rather than minor syntax cleanups.

Curveball & Edge-Case Stress Tests

6 Deep Dives
C1 1. Entity substitution with identical negation tokens
Question: Your negation guard checks set equality of negative tokens. What happens if a user asks: "Can I run Docker without sudo?" versus "Can I run Docker without root?"
Answer: Both queries contain the token "without", so the lexical guard evaluates them as having matching polarity. The final decision falls entirely on the vector similarity score from the embedding model. If the cosine score between the queries meets the 0.85 threshold, a cache hit occurs; otherwise, it misses. The guard detects polarity inversions rather than fine-grained entity replacements.
💡 What to keep in mind
Do not claim the lexical check provides full semantic parsing. Acknowledge that entity verification requires cross-encoders or structured entity extraction.
C2 2. Serialized vector scaling in Python memory
Question: In semantic_cache.py, you run json.loads on every cached item in a loop. What happens to your CPU when you reach 100,000 cached prompts?
Answer: This approach creates an immediate bottleneck because loading thousands of JSON strings into Python memory wastes CPU cycles and spikes garbage collection overhead. At 100,000 items, sequential dot products in Python take hundreds of milliseconds, defeating the purpose of the cache. Scaling requires moving vector searches out of application memory and into a native vector database running an approximate nearest neighbor index.
💡 What to keep in mind
Never defend linear scans for large datasets. Acknowledge that the current design fits small prototypes and requires native vector search engines for production scale.
C3 3. Verification of p95 percentile claim
Question: Your documentation states that p95 latency dropped by 99.3 percent. Where is your automated load test suite, and how did you verify that this was p95 rather than mean latency?
Answer: The project currently lacks a committed automated load test suite such as Locust or k6. The figure was calculated from manual test series comparing cold local model inference with warm semantic hits recorded by the application timer. Adding an automated benchmarking suite to record true percentiles under concurrent traffic is an immediate next step for the project.
💡 What to keep in mind
Do not fabricate a benchmark harness that is absent from the repository. Take ownership of the measurement methodology and explain how formal tests should be built.
C4 4. Concurrency gap in rate limiting checks
Question: In rate_limiter.py, you check whether current_count exceeds the limit in Python after executing the pipeline. What happens if multiple requests execute that pipeline concurrently?
Answer: Because the quota evaluation occurs in application memory after the pipeline completes, multiple simultaneous requests can read the same count before updating, causing slight over-admission. While the pipeline executes commands atomically, it does not lock the key against concurrent reads. Absolute atomicity requires moving the entire check-and-insert logic into a single Redis Lua script executed directly on the server.
💡 What to keep in mind
Differentiate between atomic command execution via pipelines and transactional read-modify-write safety. Mentioning server-side Lua scripts demonstrates deep Redis expertise.
C5 5. Thundering herd after circuit cooldown
Question: Your circuit breaker trips open for 30 seconds. At second 31, if hundreds of requests arrive, what happens to your primary model?
Answer: Once the Redis state key expires at second 31, all incoming requests read the state as closed and attempt to call the primary model at once. This creates a thundering herd problem that can crash an already struggling primary endpoint. A resilient design implements a half-open state that allows only a single canary request through while continuing to route remaining traffic to the backup.
💡 What to keep in mind
Simple time-to-live expiration provides automatic recovery but lacks traffic throttling on restart. Highlighting canary testing shows an understanding of real-world distributed failure patterns.
C6 6. Client identity spoofing via payload
Question: In main.py, client_id is read from the request payload. Can a malicious user bypass your rate limiter by passing random identifiers?
Answer: Yes, accepting the identifier from the payload allows clients to circumvent quotas by generating unique strings. This option was included solely to simplify manual testing through documentation interfaces. In production, client identity must be extracted strictly from authenticated tokens or trusted reverse-proxy headers like X-Forwarded-For.
💡 What to keep in mind
Separate testing convenience from security architecture. Emphasize that production rate limiting depends on cryptographic tokens or verified IP addresses.

AutoData

Automated Multi-Hop Synthetic QA Dataset Generation via Corrective RAG and Multi-Agent Validation
Problem & Goal System Architecture (SVG) Key Files Request Flow Claims Status (6) Interview Q&A (13) Curveballs (6) 15-Line Revision

Problem Statement & Architectural Context

Foundational

Standard synthetic dataset generation pipelines produce trivial, single-hop questions easily solved through naive keyword matching, or they generate hallucinatory and ungrounded content. This prevents smaller language models from learning robust multi-step reasoning during fine-tuning. AutoData solves this by creating an autonomous, adversarial multi-agent pipeline inspired by Meta FAIR research that forces questions to synthesize facts across disjoint context chunks. It uses a Weak-Strong solver gap to filter out questions that are either trivial or unanswerably flawed.

System Architecture Blueprint

Inline Vector SVG

End-to-End Architectural Flow Sequence:

  1. 1 Ingest raw documents into ChromaDB using FastEmbed embeddings.
  2. 2 Dynamically extract core multi-hop topics from sample chunks using an LLM.
  3. 3 Retrieve candidate chunks and evaluate reasoning depth with the CRAG evaluator.
  4. 4 Rewrite the search query and re-query ChromaDB up to four times if context is shallow.
  5. 5 Generate a multi-hop question, reference answer, and weighted rubric in the Challenger node.
  6. 6 Execute the Weak Solver and Strong Solver concurrently on the question.
  7. 7 Grade both solver answers against the rubric in the Judge node.
  8. 8 Route back to the Challenger with diagnostic feedback if the question is too easy or illogical.
  9. 9 Persist verified question-answer pairs to the final JSON dataset upon loop convergence.

src/graph/graph.py: Constructs the LangGraph StateGraph, registers parallel solver edges, defines route_after_judge conditional routing, and exports visual mermaid diagrams.

src/agents/solvers.py: Contains weak_solver_node wrapping Llama 3.1 8B and strong_solver_node wrapping Gemma 31B, both constrained strictly to the provided context.
src/agents/judge.py: Contains judge_node which evaluates solver outputs against individual rubric criteria with weights from positive five to negative five, returning percentage scores.

Step-by-Step Request Flow

11 Steps
  1. 1 The orchestrator in main.py initializes the ChromaDB client and calls extract_topics() to sample ten chunks and extract three to five core concepts.
  2. 2 For each extracted topic, main.py enters a retrieval loop, querying ChromaDB for the top two semantic chunks.
  3. 3 src/agents/crag_evaluator.py inspects the retrieved chunks; if deemed shallow or tangential, it rewrites the query and re-queries up to four times.
  4. 4 Once context is approved, main.py packages the data into AutoDataState and executes app.invoke() on the compiled LangGraph.
  5. 5 In src/agents/challenger.py, the Challenger node analyzes the context chunks and synthesizes a question, reference answer, and weighted rubric.
  6. 6 The graph fans out into parallel branches: src/agents/solvers.py runs Llama 3.1 8B in weak_solver_node and Gemma 31B in strong_solver_node.
  7. 7 Both solver answers fan into src/agents/judge.py, where judge_node scores each answer independently against the rubric criteria.
  8. 8 The conditional router route_after_judge() in src/graph/graph.py evaluates the resulting percentage scores.
  9. 9 If the Weak Solver scores above 50%, the router flags the question as too easy and loops back to Challenger with difficulty-scaling instructions.
  10. 10 If the Strong Solver scores below 70%, the router flags the question as illogical and loops back to Challenger with grounding-correction instructions.
  11. 11 If the Weak Solver scores at or below 50% and the Strong Solver scores at or above 70%, the loop terminates, and main.py writes the validated pair to disk.

Q1 1. End-to-end walkthrough of one QA pair
Question: Can you walk me through the complete lifecycle of how a raw document chunk becomes an accepted QA pair in your pipeline?
Answer: The pipeline starts in main.py by extracting a topic and retrieving two candidate chunks from ChromaDB using FastEmbed embeddings. Next, evaluate_context() in src/agents/crag_evaluator.py checks whether the chunks have sufficient multi-hop depth, rewriting the search query if the context is too shallow. Once approved, the context enters LangGraph in src/graph/graph.py, where challenger_node generates a question, reference answer, and weighted rubric. Llama 3.1 8B and Gemma 31B answer the question in parallel within src/agents/solvers.py. Finally, judge_node in src/agents/judge.py evaluates both answers; if Gemma scores 70% or higher and Llama scores 50% or lower, main.py appends the pair to output/synthetic_dataset.json.
💡 What to keep in mind
Emphasize that retrieval validation via CRAG happens before the LangGraph generation loop to conserve local GPU compute. Note that the retriever fetches exactly two chunks ($k=2$). Avoid claiming that the entire ingestion and generation process is managed within a single graph node.
Q2 2. Challenger, Solver, and Judge roles
Question: What are the distinct responsibilities, inputs, and outputs of the Challenger, Solver, and Judge agents?
Answer: In src/agents/challenger.py, the Challenger takes context chunks and previous iteration critique, outputting a multi-hop question, reference answer, and Pydantic rubric. The Solvers in src/agents/solvers.py take the generated question and raw context chunks without ever seeing the reference answer or rubric, outputting unstructured text solutions from Llama 3.1 8B and Gemma 31B. In src/agents/judge.py, the Judge receives the question, reference answer, rubric, and both solver answers. It evaluates each rubric criterion, outputting percentage scores and diagnostic feedback for both models.
💡 What to keep in mind
Solvers are strictly blinded to the reference answer and rubric to avoid evaluation leakage. The Challenger defines the evaluation rubric dynamically at question creation time. Avoid stating that the Judge invents its own criteria during evaluation.
Q3 3. What adversarial means in this project
Question: What makes this architecture truly adversarial compared to standard synthetic generation scripts?
Answer: Standard synthetic data pipelines prompt an LLM once to produce a question and answer, leaving quality and difficulty unverified. In AutoData, the Challenger is pitted directly against two opposing solvers in a cyclic LangGraph loop defined in src/graph/graph.py. If the Weak model solves the question, the Challenger's output is rejected as too easy, forcing it to generate a more difficult multi-hop question. If the Strong model fails, the output is rejected as illogical. The Challenger must iteratively adapt its generation strategy in src/agents/challenger.py based on Judge feedback until it successfully stumps the weak solver while remaining solvable for the strong one.
💡 What to keep in mind
The adversary is the capability gap between two different model sizes rather than a neural discriminator. This adversarial rejection sampling increases generation latency compared to one-shot prompting. Avoid implying that this uses gradient-based adversarial training like a GAN.
Q4 4. Multi-hop questions and hop verification
Question: How does the pipeline generate multi-hop questions, and how do you verify that a question actually requires multiple hops?
Answer: In src/rag/vector_store.py, ChromaDB retrieves two distinct context chunks separated by divider tokens. The system prompt in src/utils/prompts.py explicitly commands the Challenger to identify facts across both separate chunks and synthesize a question requiring synthesis between them. Verification is enforced through the rubric generated in src/agents/challenger.py. The rubric defines distinct criteria for facts located in Chunk 1 and Chunk 2, alongside a combination criterion. If a solver only identifies facts from a single chunk, the Judge in src/agents/judge.py withholds points, ensuring genuine multi-hop dependency.
💡 What to keep in mind
Verification relies on structured rubric enforcement rather than a formal knowledge graph path traversal. Multi-hop synthesis occurs in the context window across the top two retrieved chunks. Avoid claiming that chunks are explicitly linked by document metadata in ChromaDB.
Q5 5. The Weak-Strong loop and the 20-point gap
Question: Why pair Llama 3.1 8B with Gemma 31B, and how was the 20-point accuracy gap established?
Answer: Llama 3.1 8B was selected as the Weak model and Gemma 31B as the Strong model in src/config.py due to their clear differentiation in multi-step reasoning capabilities. The 20-point gap is an operational acceptance gate defined in route_after_judge within src/graph/graph.py, requiring strong_score >= 70 and weak_score <= 50. This mathematical delta of at least 20 percentage points ensures that accepted questions fall into the desired difficulty band. It guarantees that the question exposes a smaller model's reasoning deficiency while remaining logically sound for a larger model.
💡 What to keep in mind
Clarify that the 20 points is a programmatic routing threshold ($70\% - 50\% = 20\%$) rather than an offline benchmark score measured on academic datasets. Gemma 31B was chosen because its larger parameter scale provides reliable reference answers. Avoid claiming that this gap was measured across MMLU or GSM8K benchmarks.
Q6 6. Judge reliability and bias
Question: How does the Judge determine if an answer is correct, and how do you mitigate LLM judge bias?
Answer: In src/agents/judge.py, the Judge grades solver answers strictly against the fine-grained rubric criteria generated by the Challenger, assigning weights between positive five and negative five. To minimize subjectivity, the Judge prompt in src/utils/prompts.py instructs the model to ignore stylistic phrasing and evaluate only underlying factual logic. The Judge operates at temperature 0.1 for deterministic grading. Because the Judge runs Gemma 31B—the same model family as the Strong solver—there is a potential self-preference bias, which we mitigate by evaluating answers against explicit, externalized rubric criteria.
💡 What to keep in mind
Using explicit criteria-level scoring reduces the variance associated with holistic single-score LLM evaluations. Running the Judge on the same model family as the Strong solver introduces minor stylistic bias. Avoid claiming that LLM-as-a-judge evaluations are completely free from bias.
Q7 7. DeepEval metrics and gating reality
Question: How are metrics like Faithfulness, Precision, and Relevancy implemented in your evaluation gates?

Problem Statement & Architectural Context

Foundational

Traditional multi-agent architectures rely on a centralized router agent that decides every execution step synchronously, creating a latency and throughput bottleneck. Problem Statement & Architectural Context

Foundational

Standard Retrieval-Augmented Generation concatenates 10 to 15 raw document chunks into a single large prompt, creating severe attention degradation and "lost-in-the-middle" position bias where central facts are ignored. Long-context verification scales self-attention compute quadratically, resulting in high inference latency and excessive token consumption on large models. SpecuRAG solves this by decoupling contextual drafting across lightweight parallel models from verification on a generalist judge without passing raw chunks to the verifier.

Percentages

Arithmetic Foundations
📐 Core Formulae
Percentage Increase/Decrease = (Absolute Difference / Original Value) * 100. Multiplier Concept: A p percent increase equals a multiplier of (1 + p/100); a p percent decrease equals (1 - p/100).
⚡ Shortcut Techniques
Use fraction-to-percentage conversions for speed (1/6 = 16.66%, 1/7 = 14.28%, 1/8 = 12.5%, 1/9 = 11.11%, 1/12 = 8.33%). For successive percentage changes of a% and b%, the net effective change is (a + b + (a * b) / 100)%.
⚠️ Common Pitfall / Trap
Applying percentage changes to the wrong base. If value A is 25% greater than B, value B is not 25% less than A (B is 20% less than A because the base shifts from B to A).
💡 Worked Example & Solution
Problem: The price of a commodity increases by 25%. By what percentage must consumption be reduced so that overall expenditure remains unchanged?
Solution Breakdown:
Let original price = 100, original consumption = 100, expenditure = 10,000. New price = 125. Required consumption = 10,000 / 125 = 80. Reduction in consumption = 100 - 80 = 20. Percentage reduction = (20 / 100) * 100 = 20%.

Ratio & Proportion

Ratios & Variations
📐 Core Formulae
Duplicate Ratio of a:b = a^2 : b^2. Triplicate Ratio = a^3 : b^3. Sub-duplicate Ratio = sqrt(a) : sqrt(b). Compounded Ratio of (a:b) and (c:d) = (ac : bd). If a/b = c/d, then by Componendo and Dividendo: (a + b) / (a - b) = (c + d) / (c - d).
⚡ Shortcut Techniques
To combine overlapping ratios like A:B = 2:3 and B:C = 4:5, multiply the first ratio by 4 and the second ratio by 3 to equate the shared term B, producing A:B:C = 8:12:15.
⚠️ Common Pitfall / Trap
Adding constants directly to ratio terms without understanding that ratios express relative proportions rather than absolute values. (a/b is not equal to (a+k)/(b+k)).
💡 Worked Example & Solution
Problem: Divide 1200 dollars between A, B, and C such that A's share is 2/3 of B's share, and B's share is 1/4 of C's share.
Solution Breakdown:
A/B = 2/3 implies A:B = 2:3. B/C = 1/4 implies B:C = 1:4 = 3:12. Combining gives A:B:C = 2:3:12. Total parts = 2 + 3 + 12 = 17 parts. Share of A = (2/17) * 1200 dollars. Share of B = (3/17) * 1200 dollars. Share of C = (12/17) * 1200 dollars.

📐 Core Formulae

⚡ Shortcut Techniques
Relative Speed: When two objects move in opposite directions, relative speed is (S1 + S2). When moving in the same direction, relative speed is |S1 - S2|. When distance is constant, speed is inversely proportional to time (S1 / S2 = T2 / T1).
⚠️ Common Pitfall / Trap

📐 Core Formulae

Chance & Stochasticity
📐 Core Formulae
